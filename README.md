# Тест DISC — мультиязычный статический сайт

Бесплатный онлайн-тест поведенческих стилей DISC на 13 языках. Статический сайт: результат считается в браузере. Единственная серверная часть — скрипт Google Apps Script, который отправляет участнику письмо с результатом и ведёт базу результатов в Google Таблице.

**Языки:** English, Русский, Español, 简体中文, 繁體中文, العربية, Português, Français, Deutsch, 日本語, हिन्दी, Bahasa Indonesia, Türkçe, Polski.

## Как собрать

```bash
node scripts/make-assets.js  # один раз и после смены title, названий профилей или стилей в локалях: иконки, og-картинки языков, 16 профилей (src/assets/og/profiles/) и 10 пар совместимости (src/assets/og/pairs/)
node scripts/fetch-fonts.js  # только при смене набора шрифтов: woff2 в src/assets/fonts/
node scripts/make-pdf.js     # после правки блоков теста, названий профилей или текстов print.*: PDF в src/assets/pdf/
node build.js            # (или npm run build) пересобирает docs/ для всех языков
LANGS=ru node build.js   # быстрая сборка одного языка для локальной проверки
node scripts/check-links.js  # после сборки: все внутренние ссылки и файлы собранного сайта существуют
node scripts/serve.js    # (или npm run serve) открыть http://localhost:8765 для проверки
npm run deploy           # проверить локали, собрать, закоммитить и запушить
```

После сборки закоммитьте изменения в `docs/` и запушьте в `main` — GitHub Pages опубликует их автоматически (обычно за 1–2 минуты).

### Sitemap и даты изменения

`docs/sitemap.xml` — индекс, в нём 14 файлов `sitemap-<язык>.xml` (страницы и PDF одного языка). Страницы «Обратная связь» закрыты `noindex, follow` и в sitemap не входят. В Search Console достаточно отправленного `sitemap.xml`; чтобы видеть индексирование по каждому языку, отправьте и отдельные `sitemap-ru.xml` и т. д.
Дата `lastmod` и строка «Обновлено …» считаются по содержимому самой страницы: сборка хранит отпечаток текста в `src/lastmod.json` и ставит сегодняшнюю дату только страницам, текст которых изменился. Файл нужно коммитить вместе с `docs/`. Сборка части языков (`LANGS=ru`) записи остальных языков не трогает.

### IndexNow (Bing, Яндекс)

Через 1–2 минуты после пуша сообщите поисковикам об изменённых страницах:

```bash
node scripts/indexnow.js          # страницы docs/, изменённые последним коммитом
node scripts/indexnow.js HEAD~3   # изменённые за последние три коммита
node scripts/indexnow.js --all    # все адреса sitemap (после крупных изменений)
node scripts/indexnow.js --dry    # только показать список
```

Ключ — `indexNowKey` в `site.config.json`; сборка кладёт файл `<ключ>.txt` в корень сайта, по нему поисковики проверяют владельца. Ответ 200 или 202 — принято. Google IndexNow не поддерживает: для него sitemap и «Проверка URL» в Search Console.

## Как изменить тексты

Все тексты живут в `src/locales/<язык>.json`: `ui` — интерфейс, `styles`/`profiles` — описания стилей и профилей (у каждого профиля есть ещё `careers`, `team` и `with` — подходящие роли, поведение в команде и советы по общению с четырьмя стилями), `content` — тексты страниц «Что такое DISC», «Расшифровка результатов», «DISC по цветам», «Тест в PDF», «DISC для команды», «DISC и MBTI», «Совместимость стилей», FAQ, «О проекте», «Конфиденциальность» (массивы разделов должны быть одинаковой длины во всех языках). Меняйте значения, не меняя ключи. Затем:

```bash
node scripts/validate-locale.js   # проверит все локали против ru.json
node build.js
```

Раздел текстовой страницы — объект `{ h, p, ul, ol, after }`: заголовок, абзацы, маркированный или нумерованный список и абзацы после списка (нужны только `h` и один из остальных ключей).

**Источники.** Список литературы к странице «Что такое DISC» лежит не в локалях, а в константе `SOURCES` в `build.js`: библиографические описания одинаковы во всех языках, потому что названия работ приводятся на языке оригинала. Переводятся только заголовок раздела (`content.disc.sourcesTitle`), вводка (`content.disc.sourcesLead`) и подписи вида «Исследование» (ключи `sources.kind.*`). Каждая запись — объект `{ kind, text, url }`; `kind` выбирает подпись. Добавляя источник, сверяйте выходные данные с карточкой издателя или научной базы и ставьте постоянную ссылку (`doi.org`, архив, страница издателя).

**Дата обновления.** Под текстом каждой контентной страницы выводится дата последнего изменения её исходников (ключ `pages.updated`). Дата берётся из истории git по тем же файлам, что и `lastmod` в `sitemap.xml`; у файлов с незакоммиченными правками ставится сегодняшняя.

Чтобы добавить сразу много ключей на всех языках, удобнее не править десять файлов вручную: положите фрагмент вида `{"ui": {...}, "content": {...}}` в отдельный файл и влейте его в каждую локаль:

```bash
node scripts/merge-locale.js фрагмент-ru.json ru   # ключи встают на места по эталону, файл переформатируется
node scripts/trim-descriptions.js                  # покажет описания длиннее 170 символов (--write — подрезать)
```

**Description страниц профилей** — ключ `profiles.<код>.metaDesc`: своё описание профиля, после которого сборка добавляет призыв `pages.profile.descCta`, если он помещается целиком (всего до 155 знаков, в японском и китайском — до 90); если описание длиннее, сборка выводит предупреждение. Шаблонные description (пары совместимости) сборка обрезает по концу предложения, а не на полуслове. **Шрифт заголовков** (Unbounded, в арабской версии Noto Kufi Arabic) используется в одном весе — 500: файлы веса 600 сборка не подключает, поэтому в стилях для `var(--font-head)` не ставьте `font-weight` больше 500, иначе браузер нарисует искусственный полужирный. **Title** держите в пределах ~600 px в выдаче Google (≈55–60 латинских или кириллических знаков, ≈30 иероглифов): главное слово — в начале. «Типы личности DISC» — запрос страницы «Четыре стиля»; каталог 16 профилей называется «16 профилей DISC», чтобы не спорить с ней. Текст каталога под таблицей профилей — `content.profiles.sections`, подписи таблицы — `pages.profiles.tableTitle`, `colLead`, `colPure`; заголовок над карточками на страницах пар — `pages.compat.together`. Схему цветов `docs/img/disc-colors-<язык>.svg` рисует сборка из названий цветов и стилей. **Призыв после вводного абзаца** контентных страниц — ключи `cta.inline` (общий), `cta.inlineProfile`, `cta.inlineResults`, `cta.inlinePdf`, `cta.inlinePair`, `cta.inlineColors`; тексты страницы 404 — `notFound.title`, `notFound.text`.

**Важно:** порядок стилей в 24 блоках вопросов (`BLOCK_KEYS` в `src/template.html`) менять нельзя — от него зависят коды результатов, которые уже разосланы участникам.

**Типографика, которую добавляет сборка.** Во французских текстах пишите обычный пробел перед `: ; ! ?` и внутри `« »`: сборка сайта и PDF (`src/typo.js`) заменяет его узким неразрывным, чтобы знак не переносился на новую строку. В арабских текстах числа со знаком (`+24`, `−24`) пишите как есть: сборка ставит перед знаком невидимую метку направления, иначе знак отображается после числа. Сами управляющие символы в локали не вставляйте. После правки утверждений теста, названий профилей или текстов `print.*` пересоберите PDF: `node scripts/make-pdf.js`.

## Как добавить язык

1. Скопируйте `src/locales/en.json` в `src/locales/<код>.json`, переведите (эталон смысла — `ru.json`), укажите `lang`, `name`, `dir` (`rtl` для арабского/иврита) и `dateLocale`. Код языка — он же папка на сайте, значение `lang` у страниц и значение параметра «Язык сайта» в Метрике; пишется строчными (`zh-hant`).
2. Добавьте код в `languages` в `site.config.json` (порядок в списке — порядок в меню языков; при необходимости `hreflang`, например `"pt": ["pt", "pt-BR"]`, `"zh-hant": ["zh-Hant", "zh-TW", "zh-HK"]`).
3. В `build.js`: флаг в `FLAGS`, локаль Open Graph в `OG_LOCALE`; если нужны особые шрифты (не латиница/кириллица) — запись в `FONTS` (пустой `families` означает «только системные шрифты», так сделано для `zh`, `zh-hant`, `ja`) и такая же в `FONTS` в `scripts/make-pdf.js`; если язык на латинице с диакритикой вне Latin-1 (польский) — код в `LATIN_EXT`, чтобы подмножество latin-ext загружалось заранее. Перед этим проверьте, что нужные буквы в шрифте настоящие: у Golos Text из Google Fonts буквы ğ и Ğ собраны без бревиса, поэтому у турецкого своя запись в `FONTS` — основной текст системным шрифтом. Для языка с региональными вариантами (как `zh-TW` → `zh-hant`) — правило в подсказке языка браузера в `src/common.js`. Для китайского и японского лимит description короче — `MAX`/`MIN` в `scripts/trim-descriptions.js`.
4. Напишите для языка тексты платной услуги — `content.offer`, `content.refund` (с ключом `note`), `content.services.docs`, `content.policy.purchase`, `content.privacy.purchase`, `content.product` (с `block.soon`, без листов образца, `pay` и `extendedMail`) и `ui["nav.offer"]`; образец структуры — `en.json`. Вставить готовый фрагмент в локаль, не переформатируя файл: `node scripts/add-report-texts.js <фрагмент.json> <код>`. Что означают ключи — раздел «Страницы „Услуги“, „Публичная оферта“ и „Условия возврата“».
5. Обновите число языков в текстах всех локалей: `content.about.title` («…на 13 языках»), первый абзац `content.about.sections[0]` («Сайт работает на тринадцати языках») и в русской — ответ `content.business.faq[1].a` («Сам тест бесплатно доступен на 13 языках»).
6. `node scripts/validate-locale.js`, `node scripts/trim-descriptions.js <код>`, затем `node scripts/make-assets.js` (og-картинка), `node scripts/make-pdf.js <код>`, `node build.js` и `node scripts/check-links.js` (внутренние ссылки собранного сайта). Проверьте образцами, что PDF краткого отчёта с блоком о расширенном отчёте остаётся на двух листах у всех 16 профилей.
7. Метрика: ничего настраивать не нужно — счётчик один на весь домен, новые страницы попадают в него автоматически, а параметр визита «Язык сайта» получает код нового языка из `lang` локали.

## Как снять язык

Так снят хинди (2026-10-25, решение заказчика: за месяц один посетитель из ~7 400, ни одного начатого теста).

1. Уберите код из `languages` и добавьте в `"retiredLanguages"` в `site.config.json`: код → язык, куда вести (`{ "hi": "en" }`). Сборка пишет на месте каждой страницы снятого языка (`/hi/`, `/hi/profiles/d/` …) страницу переадресации на ту же страницу целевого языка: мгновенный `meta refresh` (Google считает его постоянной переадресацией), `canonical` на целевую страницу и скрипт, который переносит хэш, — разосланные ссылки с `#r=…`, `#u=…`, `#c=…` продолжают работать. В меню языков, sitemap, hreflang и 404 снятого языка нет; запомненный в браузере выбор (`disc.lang`) сайт пропускает.
2. Удалите локаль и файлы языка: `src/locales/<код>.json`, `src/assets/og/<код>.png`, `og/pairs/<код>-*.png`, `og/profiles/<код>-*.png`, `src/assets/pdf/disc-test-<код>.pdf`; записи в `FONTS`, `FLAGS`, `OG_LOCALE` (`build.js`) и `FONTS` в `scripts/make-pdf.js`; особые шрифты языка — строки в `src/assets/fonts/fonts.css`, файлы `woff2` и семейство в `scripts/fetch-fonts.js`. Из git файлы не пропадают: язык можно вернуть.
3. Число языков в текстах всех локалей (пункт 5 раздела выше), проверки `scripts/test-apps-script.js`, список `LANGS` в `private/server/src/admin.js` и языки в серверных проверках (`test/smoke.js`, `test/short-report-pages.js`).
4. Сборка, `node scripts/validate-locale.js`, `node scripts/check-links.js`, `node scripts/test-apps-script.js`, выкладка сервера (ядро без снятого языка: письма на нём уходят по-английски), публикация.

## Свой домен

1. В `site.config.json` укажите `"siteUrl": "https://ваш-домен.com"` и `"customDomain": "ваш-домен.com"` — сборка создаст файл `docs/CNAME` и правильные canonical/hreflang.
   Для подтверждения сайта в Google Search Console (ресурс с префиксом в URL, способ «HTML-тег») впишите токен из тега `<meta name="google-site-verification" content="…">` в `"googleSiteVerification"` и пересоберите; пустое значение — тег не выводится. Ресурс уровня домена подтверждается только TXT-записью DNS у регистратора. Для Яндекс Вебмастера (способ «Метатег») аналогично впишите значение `content` в `"yandexVerification"`.
   **Аналитика.** `"yandexMetrikaId"` — номер счётчика Яндекс.Метрики; `"analyticsMode"`: `"always"` — счётчик загружается сразу, уведомление о cookie лишь информирует (одна кнопка «Понятно»); `"optin"` — счётчик загружается только после кнопки «Принять», кнопка «Только необходимое» оставляет сайт без аналитики. Тексты `consent.text`, `consent.details` и абзацы страницы «Конфиденциальность» о Метрике написаны для режима `always`; при переходе на `optin` их нужно переписать (формулировки «с вашего согласия», «без согласия счётчик не загружается»). Код счётчика в `src/common.js`. Хэш адреса с личными данными (`#r=…` — код результата с именем и e-mail, `#u=…` — ключ отписки) убирается из адресной строки до загрузки счётчика и хранится в записи истории браузера (`dataHash()`): счётчик сам читает адрес страницы — в первом запросе (он уходит и при `defer:true`), в карте кликов, при щелчке по внешней ссылке, — поэтому одной ручной отправки просмотра мало. Код страниц читает такой хэш через `dataHash()`/`pageHash()`, а не из `location.hash`, и не пишет его в разметку (в адреса ссылок). Исключение с 2026-10-22 (решение заказчика): экран результата после загрузки кладёт в адресную строку ссылку на отчёт без e-mail (`showHash()`), ту же, что копирует кнопка «Скопировать ссылку», — чтобы адрес из строки браузера можно было переслать. Эту ссылку (ответы, дата и имя, если оно есть в коде) счётчик видит, о ней говорят тексты о данных на 13 языках; e-mail в адрес не попадает: старая ссылка с e-mail при открытии сначала убирается из адреса, до загрузки счётчика, и возвращается без e-mail. Каждый просмотр передаёт параметр визита «Язык сайта» с кодом языковой версии (en, ru, de…): отчёт «Отчёты → Содержание → Параметры визитов», там же можно выбрать цели и смотреть конверсию по языкам; для остальных отчётов — сегмент по этому параметру. ## Аналитика по языкам, согласие на обработку данных и политика

**Режим аналитики.** Сейчас `"analyticsMode": "always"`: счётчик загружается сразу во всех языках, уведомление о cookie лишь информирует (решение заказчика от 2026-10-11; режим «после согласия» в 13 языках был опубликован несколько часов 11 октября и отменён). На экране своего результата (тест пройден в этом браузере) уведомление в режиме «сразу» считается прочитанным и убирается (`window.discNoticeSeen` в `src/common.js`, с 2026-10-21): человек видел его все 24 блока, а на телефоне оно закрывало кнопку отчёта. В режиме «после согласия» так не делается. Сборка умеет и раздельный режим: `"analyticsMode": "optin"` вместе с `"analyticsAlwaysLangs": ["ru"]` — в перечисленных языках счётчик сразу, в остальных только после кнопки «Принять». Текст уведомления в режиме «после согласия» — `ui["pd.cookieAsk"]`, в режиме «сразу» — `ui["consent.text"]`; сборка подставляет нужный сама. Кто в дни режима «после согласия» нажал «Только необходимое», тому счётчик не загружается и в режиме «сразу» (`src/common.js`).

**Согласие на обработку персональных данных и новая редакция «Конфиденциальности»** готовы и выключены: `"pdConsent": false`. Включать вместе с переводом `sendEndpoint` на свой сервер (этап Е плана `private/PRODUCTION-PLAN.md`): тексты описывают хранение данных в России, а прежний скрипт Google согласие не записывает. При `"pdConsent": true`:

- в форме «Получите краткий отчёт в PDF на e-mail» (на экране результата она стоит сразу под графиком и числами, до описания профиля) и в форме обратной связи появляется отдельная галочка (`ui["pd.consent"]`, по умолчанию снята) со ссылками на страницу согласия и на «Конфиденциальность»; без неё форма не отправляется (`ui["pd.required"]`), запрос несёт `consent: true` и `consentV` — дату редакции;
- строится страница `/consent/` на всех языках (`content.consentDoc`; noindex, вне sitemap);
- страница «Конфиденциальность» строится из `content.policy` (те же девять разделов на всех языках); в языках с офертой перед разделом о правах встаёт `content.policy.purchase`, в русской версии в конце — полный текст политики `content.policy.legal`. В режиме «после согласия» в разделе Cookie появляется кнопка «Изменить выбор cookie» (`{reset}`); в режиме «сразу» сборка её убирает;
- подробности уведомления о cookie берутся из `ui["pd.cookieDetails"]` (без названий прежних сервисов).

`"pdVersion"` — дата редакции политики и согласия (`ГГГГ-ММ-ДД`): её показывают страницы (`{date}`), а сервер сохраняет рядом с отметкой о согласии вместе с текстом (`backend/apps-script/Code.gs` → `DATA[язык].pd`). **После правки текста согласия или галочки нужно сменить `pdVersion`** и выложить серверную часть: по дате сервер различает, на какой текст согласился человек.

Подстановки в этих текстах: `{owner}` — оператор (в языках с офертой — исполнитель из оферты с ИНН, в остальных — строка реквизитов из подвала), `{email}`, `{contact}` и `{privacy}` — ссылки на страницы, `{consent}` — ссылка на страницу согласия с текстом `ui["pd.consentLink"]`, `{date}` — дата редакции, `{offer}` — ссылка на оферту. **Если почтовый сервис не ответил.** Сервер ставит письмо с результатом на повтор и отвечает сайту `queued: true`; экран результата показывает `ui["share.sendQueued"]` («письмо придёт позже, отправлять ещё раз не нужно») вместо `share.sendFailed` с кнопкой повтора. Локальная проверка — заглушка `POST /mock-queued` в `scripts/serve.js`: `SEND_ENDPOINT=http://localhost:8765/mock-queued node build.js`.

**О стране хранения данных говорит только русская версия** (решение заказчика от 2026-10-11): в остальных 13 языках в политике, согласии и уведомлении о cookie сказано «на сервере, который владелец сайта арендует у хостинг-провайдера», без страны и без слов о передаче за границу. При правке этих текстов и при добавлении языка страну не называть. Абзац об аналитике, раздел Cookie и `pd.cookieDetails` во всех 13 языках написаны под режим «сразу» («отключить сбор можно в настройках браузера»): если какой-то язык переводится в режим «после согласия», эти три места в нём нужно переписать.

Локальная проверка без правки `site.config.json`: `PD_CONSENT=1 SEND_ENDPOINT=https://api.disc-test.org/ node build.js`, просмотр на `localhost:8765` (свой сервер принимает запросы с этого адреса); писем не будет, если на сервере включён проверочный режим (`MAIL_DRYRUN=1`, `private/infra/SERVER.md`). После проверки — `git checkout src/lastmod.json && node build.js`: иначе в `docs/` останется сборка с адресом своего сервера, а в датах страниц — следы проверки.

### Обезличенный счёт прохождений (страницы «Профили» и «Прохождения» в панели)

С 2026-10-12 сервер считает все прохождения теста, а не только результаты, отправленные на e-mail. Ключ `"profileStats": true` в `site.config.json` (работает только вместе с `sendEndpoint`): в момент, когда участник отвечает на последний блок, страница шлёт на `sendEndpoint` один запрос `{"action":"stat","lang":"<язык>","profile":"<профиль>"}` (`sendStat` в `src/template.html`). Имени, e-mail, ответов и кода результата в запросе нет. Повторное открытие готового результата — по ссылке, из памяти браузера, после перезагрузки — запрос не шлёт; ответ странице не нужен, сбой молча пропускается.

С вечера 2026-10-12 тот же ключ включает второй запрос — отметку о начале теста: по кнопке «Начать тест» страница шлёт `{"action":"start","lang":"<язык>"}` (`sendStart`). В нём только язык версии; продолжение начатого теста («Продолжить») запрос не шлёт. Сервер (`handleStart`) пишет в таблицу `test_starts` язык и день по Москве — без времени и IP-адреса; с записью о пройденном тесте строка не связана, поэтому узнать, кто из начавших дошёл до конца, по ним нельзя. Пределы те же: 30 записей в час с одного адреса, в сутки — не больше 50 000 строк.

Сервер (`handleStat` в `private/server/src/main.js`) пишет в таблицу `profile_stats` профиль, язык и день по Москве: времени и IP-адреса в строке нет, с таблицей результатов она не связана. С одного адреса в час считается не больше 30 прохождений (счётчик в памяти), в сутки — не больше 20 000 строк. Панель показывает счёт на странице «Профили», источник «Все прошедшие тест»; «Приславшие результат» — прежний счёт по таблице результатов. Страница «Прохождения» (`admin.disc-test.org/passes`) показывает тот же счёт по дням: сколько раз тест в этот день начали (`test_starts`), сколько раз прошли и сколько результатов прислано, с отбором по языку и датам. Страница начинается с первого дня, за который в базе есть записи (8 октября 2026 — первые результаты на своём сервере): более ранние дни не показываются и не выбираются; за дни до начала счёта (8–11 октября) в столбцах «Начали тест» и «Прошли тест» стоит прочерк. Счёт начатых тестов идёт с вечера 12 октября: тесты, начатые раньше, есть только в «Прошли тест», а тест, начатый в один день и законченный в другой, попадает в разные строки — в отдельный день прошедших может быть больше, чем начавших.

Об этих двух записях говорят три текста в каждом из 13 языков: строка под тестом (`ui.privacy`), первый абзац раздела «Какие данные мы используем» политики (`content.policy.sections[1].p[0]`) и подробности уведомления о cookie (`ui["pd.cookieDetails"]`); в русской версии — ещё пункт 2.7 полного текста политики. **Ключ и тексты меняются только вместе**: выключая счёт, верните прежние формулировки и поставьте новую дату в `pdVersion`. Новое поле в запросе или новая запись — сначала правка этих текстов на 13 языках.

Проверка на сервере без настоящих участников: `sudo -u disc node test/stat-check.js` из `/srv/disc/app` — вторая копия службы на своём порту, проверяет обе записи (прохождение и начало теста), свои строки убирает. Локально: `node scripts/serve.js` и сборка с `SEND_ENDPOINT=http://localhost:8765/mock-send node build.js` — заглушка печатает тело запроса (после проверки пересобрать без переменной).

### Свой счёт посетителей (карточка «Сегодня и неделю назад» на «Сводке» панели)

С вечера 2026-10-20 сайт сам считает посетителей: система веб-аналитики отдаёт их с задержкой от часа до нескольких часов, а «Сводка» сравнивает сегодняшний день с тем же днём неделю назад к текущей минуте. Ключ `"visitStats": true` в `site.config.json` (только вместе с `sendEndpoint`): сборка кладёт в `<head>` каждой страницы `window.DISC_VISIT` (адрес сервера, токен, домен сайта), а `src/common.js` раз в сутки по Москве шлёт `{"action":"visit","lang":"<язык>"}`. Дату последней отметки браузер хранит в `localStorage` под ключом `disc.visit`; без `localStorage`, на чужом домене (в том числе на `localhost`) и из автоматических браузеров (`navigator.webdriver`) отметка не уходит.

Сервер (`handleVisit` в `private/server/src/main.js`) пишет в таблицу `site_visits` язык и время получения — без IP-адреса, адреса страницы и заголовков. Заголовок браузера смотрится только для того, чтобы не считать поисковых роботов, `curl` и проверки доступности. Пределы — 30 отметок в час с одного адреса и 100 000 в сутки. Служба сообщает о счёте полем `"visits":true`.

Об отметке говорят те же три текста в каждом из 13 языков (`ui.privacy`, первый абзац раздела «Какие данные мы используем» политики, `ui["pd.cookieDetails"]`) и пункт 2.7 русской политики: **ключ и тексты меняются только вместе**. Проверка на сервере — `test/stat-check.js` (раздел о посещениях).

**С 2026-10-28 (решение заказчика) панель этот счёт не показывает.** В отметку попадали роботы, которые выполняют JavaScript и представляются обычным браузером: в версиях, где своих посетителей было больше, чем у системы веб-аналитики, начавших и прошедших тест было поровну (английская версия за 21–27.10: посетителей 497 против 307, начали тест 191 против 191). Поэтому посетители и новые посетители во всех блоках панели — по системе веб-аналитики: `site_visitors` (раз в час) и для сегодняшнего дня снимок `site_visitors_now` (раз в 10 минут: сегодня к последнему полученному просмотру и неделю назад к тому же времени суток — `visitors`, `new_today`, `week_ago_upto`, `new_ago_upto`, `sql/032_visitors_now_new.sql`). Таблица `site_visits` по-прежнему пополняется.

### Скачивание краткого отчёта (кнопка «Сохранить в PDF»)

С 2026-10-20 (`"pdfDownload": true` в `site.config.json`) кнопка «Сохранить в PDF» на экране результата не открывает окно печати, а скачивает файл `DISC-<профиль>.pdf` — тот же краткий отчёт, что вкладывается в письмо с результатом (с блоком о расширенном отчёте там, где он есть в письме). Страница шлёт `POST <sendEndpoint>pdf` с кодом результата, пересобранным без имени, e-mail и должности (`savePdf()` в `src/template.html`); сервер (`handlePdf()` в `private/server/src/main.js`) собирает PDF тем же ядром и тем же Chrome, что для писем, и отдаёт файл, ничего не сохраняя ни в базу, ни в журнал. Пределы: 20 файлов в час с одного адреса, не больше шести сборок в очереди. Пока файл собирается, на кнопке «Готовим PDF…» (`share.pdfWait`); при сбое — сообщение `share.pdfFail` и прежнее окно печати. Без ключа `pdfDownload` кнопка печатает страницу, как раньше.

Цель Метрики `pdf-download` (JavaScript-событие) — файл получен; её нужно завести и в кабинете Метрики. Тексты о данных на 13 языках (`ui.privacy`, первый абзац «Какие данные мы используем» в `content.policy`, `ui["pd.cookieDetails"]`, пункт 2.8 русской политики) говорят об этом запросе: ключ и тексты меняются только вместе. Проверка на сервере: `sudo -u disc bash -c "cd /srv/disc/app && node test/pdf-check.js"` (вторая копия службы, 13 проверок, в базу ничего не пишет).

## Наблюдение за доступностью

Доступность проверяет внешний сервис UptimeRobot в аккаунте заказчика (решение от 2026-10-11; сценарий GitHub «Доступность сайта» проработал около часа и удалён). Проверки простого типа HTTP(s), ответ с кодом 200 — «работает»:

| Что | Адрес | Когда считается сбоем |
|---|---|---|
| Сайт | `https://disc-test.org/ru/` | страница не открывается |
| Серверная часть (письма, результаты, формы) | `https://api.disc-test.org/health` | служба не отвечает, не видит базу, не заданы ключи почты или включён проверочный режим без писем — во всех этих случаях ответ 503 |
| Панель администратора | `https://admin.disc-test.org/health` | служба панели не отвечает |

Адрес `/health` серверной части отвечает и на запрос HEAD, которым сервисы наблюдения спрашивают по умолчанию. Чего внешняя проверка не видит: не выполнилась ночная резервная копия, кончается место на диске, истекает сертификат (у сервиса это платная возможность; сертификаты сервера продлеваются сами) — это внутреннее наблюдение сервера (`private/infra/SERVER.md`, не сделано).

## Печатная версия теста (PDF)

Страница `/xx/pdf/` отдаёт файл `docs/pdf/disc-test-<язык>.pdf`: инструкция, 24 блока утверждений с колонками «больше всего» и «меньше всего», ключ (какому стилю принадлежит каждое утверждение), таблица подсчёта, правило определения ведущего и вторичного стиля и краткое описание 16 профилей. Файлы генерируются заранее и лежат в репозитории — на сервере ничего не считается.

```bash
node scripts/make-pdf.js          # все языки
node scripts/make-pdf.js ru de    # только указанные
```

Скрипту нужен Google Chrome или Chromium (путь можно задать переменной `CHROME_PATH`): страница печатается в PDF headless-браузером. Разметка и стили печати — в `src/print.js`; тексты — ключи `print.*` в локалях. Шрифты берутся из `src/assets/fonts` и встраиваются в файл; для китайского и японского используются системные шрифты, поэтому эти два файла заметно больше. Размер и число страниц выводятся на странице автоматически, файл попадает в `sitemap.xml`.

Перезапускать после правки: блоков теста (`blocks` в локалях), названий и описаний профилей, текстов `print.*`. После этого `node build.js` скопирует новые файлы в `docs/pdf/`.

**Сравнение «На бумаге» и «Онлайн»** (с 2026-10-25, по просьбе заказчика): сразу под вводным абзацем страницы `/xx/pdf/` — две карточки рядом (на телефоне друг под другом). В первой — три строки о бумажной версии и кнопка «Скачать PDF», во второй — три строки об онлайн-версии, пример результата (`sampleCardHTML()` из `src/intro.js`, без графика) и кнопка теста. Тексты — `content.pdf.compare` (`paperTitle`, `paper`, `onlineTitle`, `online`, `button`) во всех 13 языках; прежняя строка `cta.inlinePdf` на странице больше не выводится. Цели Метрики: `paper-pdf` — нажата любая из двух кнопок «Скачать PDF», `pdf-online` — кнопка теста в сравнении; в кабинете системы аналитики их нужно завести (типа «JavaScript-событие»).

`print.title` — одновременно заголовок первой страницы и заголовок PDF-файла в метаданных: его Google показывает в выдаче, поэтому в нём формулировки, которыми ищут печатный тест («бланк с вопросами», «Fragebogen», «para imprimir»). Японский и оба китайских PDF собираются системными шрифтами macOS (Hiragino) — запускать `make-pdf.js` для них нужно на Mac, на Linux подставятся другие шрифты.

## Письмо с результатом и база результатов (Google Apps Script)

**С 2026-10-22 форма раскрывается кнопкой «Отправить на e-mail» в карточке «Сохраните результат»** (`"resultEmail": true`, `sendFormHTML()` в `src/template.html`, по просьбе заказчика): под графиком её нет, в коротких текстах о данных (`ui.privacy`, `ui["pd.cookieDetails"]`) фразы об отправке результата возвращены, обещания «результат на e-mail» на страницах не возвращаются (решение заказчика от 2026-10-22: кнопка — тихое дополнение; журнал `PROJECT.md` от 2026-10-22). Ниже — как было с 2026-10-21 по 2026-10-22. **С 2026-10-21 формы на экране результата не было** (`"resultEmail": false` в `site.config.json`, решение заказчика): после теста участник видит результат, сохраняет краткий отчёт в PDF и копирует ссылку; новых писем с результатом, записей в базе результатов и согласий на рассылку с сайта не приходит. Код отправки, тексты формы (`ui.intro.*`, `ui.share.*`), письмо и серверная часть оставлены. Вместе с формой из 13 локалей убраны обещания «результат на e-mail» (описание сайта, `cta.text`, `home.get`, ответы в `faq`, `about`, `services`, `results`, `pdf`, `teams`, `product.compareNote`) и фразы об отправке результата в `ui.privacy` и `ui["pd.cookieDetails"]`; полные «Конфиденциальность», согласие и политика не менялись. **Вернуть форму** — убрать ключ `resultEmail` (или поставить `true`) и вернуть эти тексты (журнал `PROJECT.md` от 2026-10-21), иначе страницы будут молчать о письме, которое снова приходит.

Тест начинается без регистрации. На экране результата участник по желанию вводит имя и e-mail и нажимает «Отправить на e-mail»; тогда страница отправляет один запрос
на веб-приложение Google Apps Script, а оно:

1. записывает результат в **базу результатов** — Google Таблицу в вашем Google-аккаунте (имя, e-mail, дата, профиль, баллы, ссылка на отчёт);
2. шлёт участнику **письмо** с профилем, баллами, ссылкой на полный отчёт и **PDF-отчётом во вложении** (`DISC-<профиль>.pdf`: профиль, выраженность стилей, ключевые черты, сильные стороны, зоны роста, мотивация, общение, стресс, среда — на языке участника).

Письма уходят с адреса `senderEmail` из `site.config.json` (если ключа нет — с `feedbackEmail`, сейчас это `info@disc-test.org`). Для этого адрес должен быть добавлен в Gmail того аккаунта, где развёрнут скрипт: **Настройки → Аккаунты и импорт → «Отправлять письма как»**. Если его там нет, письма уйдут с основного адреса аккаунта; какой адрес используется, показывает функция `setup`.

Статический сайт сам не умеет ни хранить данные, ни отправлять письма, поэтому нужен этот небольшой «бэкенд» в вашем Google-аккаунте.
Он бесплатный; лимит обычного Gmail — 100 писем в сутки (Google Workspace — 1500), записи в таблицу лимитом Gmail не ограничены.

Скрипт `backend/apps-script/Code.gs` генерируется сборкой из `src/apps-script.template.js`, `site.config.json` и локалей
(тексты письма — ключи `email.*` в `src/locales/*.json`). Проверить его без Google: `node scripts/test-apps-script.js`.

### Как развернуть (один раз, около 5 минут)

1. Придумайте секретный токен (любая строка, например 24 случайных символа) и впишите его в `site.config.json` → `"sendToken"`. Выполните `node build.js` — токен попадёт и в страницы, и в `backend/apps-script/Code.gs`.
2. Откройте https://script.google.com под своим Google-аккаунтом → **Новый проект**. Удалите содержимое файла `Code.gs`, вставьте туда содержимое `backend/apps-script/Code.gs`, сохраните (⌘S). При желании измените `OWNER_COPY` (скрытая копия каждого результата вам) и `SENDER_NAME` (имя отправителя; пока оно пустое, подставляется название теста на языке участника и домен: «Тест DISC · disc-test.org», «DISC Test · disc-test.org»).
3. Выберите вверху функцию `setup` → **Выполнить** и разрешите скрипту доступ (Gmail — отправка писем от вашего имени, Google Таблицы). В журнале выполнения появятся адрес таблицы результатов и строка «Письма уходят с адреса info@disc-test.org» (или предупреждение, что адрес не добавлен в Gmail). Затем выполните `testMail`: на адрес аккаунта придут четыре образца письма с PDF (ru, en, ar, ja) — проверьте отправителя и как выглядит PDF, особенно на арабском и японском.
4. **Развернуть → Новое развёртывание → тип «Веб-приложение»**: «Выполнять от имени» — *Я*; «У кого есть доступ» — *Все* (Anyone). Нажмите **Развернуть**, разрешите скрипту отправлять почту от вашего имени и работать с Google Таблицами, скопируйте **URL веб-приложения** (`https://script.google.com/macros/s/…/exec`).
5. Вставьте URL в `site.config.json` → `"sendEndpoint"`, выполните `node build.js`, закоммитьте и запушьте.
6. Проверьте: пройдите тест с собственным e-mail. На экране результата появится «Письмо с результатом отправлено на …», письмо с PDF придёт в течение минуты (проверьте «Спам» при первом письме), а в Google Диске появится таблица «DISC Test — результаты» с первой строкой.

После правки текстов письма или скрипта: `node build.js`, затем в редакторе Apps Script замените код и сделайте
**Развернуть → Управление развёртываниями → ✎ → Новая версия → Развернуть** (URL не меняется).

PDF собирается в самом скрипте из HTML (функция `reportHtml`, встроенный конвертер Apps Script — поэтому вёрстка только таблицами и строчными стилями). Если конвертер дал сбой, письмо уходит без вложения, а в столбце «Письмо» таблицы появляется «(без PDF: …)». `ATTACH_PDF = false` отключает вложение.

Чтобы письма с `info@disc-test.org` реже попадали в «Спам», в DNS домена (Cloudflare) в SPF-запись стоит добавить серверы Google: `v=spf1 include:_spf.mx.cloudflare.net include:_spf.google.com ~all`.

Пока `sendEndpoint` пустой, кнопка «Отправить на e-mail» открывает почтовый клиент участника с готовым письмом на введённый адрес (имя и e-mail при этом попадают в ссылку и код результата), а в базу ничего не записывается.

### База результатов (Google Таблица)

Таблица создаётся автоматически при первом результате (название `SHEET_TITLE`, по умолчанию «DISC Test — результаты», лист «Результаты») и лежит в Google Диске аккаунта, от имени которого развёрнут скрипт; её ID запоминается в свойствах скрипта, так что обновление кода таблицу не меняет. Чтобы создать таблицу заранее и узнать её адрес, в редакторе Apps Script выберите функцию `setup` и нажмите **Выполнить** — адрес появится в журнале выполнения. Своя таблица: впишите её ID (из адреса `…/spreadsheets/d/<ID>/edit`) в `SHEET_ID`.

Столбцы: дата получения · время получения (время сервера) · дата теста · время теста (из кода результата) · имя · e-mail · язык · профиль (`DI`) · название профиля по-английски (на каком бы языке ни проходили тест; в письме и PDF оно остаётся на языке участника) · D, I, S, C (баллы от −24 до +24) · D %, I %, S %, C % · письмо (статус: «отправлено …», «отправлено … (без PDF: …)», «не отправлено: …», «ошибка: …») · ссылка на отчёт · код результата. Заголовки — массив `HEADERS` в скрипте.

Дата и время лежат в отдельных ячейках: дата в виде `08.10.2026` (день, месяц, год), время — `13:01:09`, оба в часовом поясе таблицы (Файл → Настройки). Вид задают `DATE_FORMAT` и `TIME_FORMAT` в скрипте. Таблицу, заведённую до 8 октября 2026 (один столбец «Получено» и один «Дата теста»), скрипт делит сам при первом обращении — при новом результате или при запуске `setup`. Запускать `setup` для этого стоит только после выпуска новой версии развёртывания: иначе прежняя версия допишет строки в старой раскладке со сдвигом на два столбца.

Строки, записанные до 8 октября 2026, содержат название на языке участника. Чтобы перевести их разом, выберите в редакторе функцию `englishProfileNames` → **Выполнить**: она заменит названия на английские по столбцу «Профиль» и ничего больше не тронет.

Как это работает: сначала запись в таблицу, потом письмо — результат сохраняется, даже если письмо не ушло (исчерпан лимит, ошибка почты). Повторная отправка того же кода (кнопка «Отправить ещё раз») строку не дублирует, а обновляет статус письма. Проверки токена и e-mail выполняются до записи, так что подделанные запросы в таблицу не попадают; текст, начинающийся с `=`, `+`, `-`, `@`, получает пробел впереди, чтобы не стать формулой; лимит новых строк — `MAX_SAVES_PER_DAY` (2000) в сутки. `SAVE_RESULTS = false` отключает базу, письма продолжают уходить.

Таблица доступна только владельцу аккаунта; поделиться ею можно обычными средствами Google Таблиц (кнопка «Настройки доступа»), скачать для Excel — «Файл → Скачать». Таблицу можно фильтровать и сортировать, добавлять свои столбцы справа: скрипт только дописывает строки, меняет ячейку «Письмо» и четыре столбца согласия на рассылку (их он находит по заголовку «Рассылка»; заголовки этих столбцов не переименовывайте).

### Рассылка: согласие и отписка

В форме «Получите краткий отчёт в PDF на e-mail» есть галочка согласия на рассылку (по умолчанию снята, текст — `share.subscribe` в локалях). Её показывает настройка `"newsletter": true` в `site.config.json`; при `false` галочки нет, всё остальное работает. Включать настройку можно только после того, как в Apps Script развёрнута версия скрипта с поддержкой рассылки: прежняя версия согласие молча игнорирует. Проверить развёрнутую версию: откройте `sendEndpoint` в браузере — в ответе должно быть `"newsletter":true`.

Что записывается. У согласившегося в строке результата заполняются четыре столбца: **Рассылка** — `да`; **Согласие получено** — дата и время; **Текст согласия** — текст у галочки на языке участника (доказательство того, на что именно человек согласился); **Ссылка для отписки**. В письмо с результатом добавляется строка «Вы согласились получать рассылку…» со ссылкой отписки. Если участник отметил галочку уже после отправки письма, строка дополняется без второго письма (запрос `{action: "subscribe"}`). Сайт показывает «Вы подписаны…» только после ответа сервера `subscribed: true`; если записать согласие не удалось, под галочкой появляется сообщение об ошибке.

Отписка. Ссылка ведёт на страницу `/unsubscribe/#u=<код>` (`/xx/unsubscribe/` на языке участника; страница закрыта от индексации). С 2026-10-25 (по просьбе заказчика) страница сама отправляет код серверу при открытии и сразу пишет «Вы отписались…» с зелёной галочкой, как страница подтверждения подписки; кнопка «Отписаться» появляется только для повтора после сбоя. Запрос шлёт скрипт страницы, а не сам переход по ссылке: сканеры ссылок в почте, которые только скачивают страницу, никого не отписывают (сканер, который выполняет скрипты, отписать может — это безопасная сторона ошибки). Сервер снимает подписку со всех строк этого адреса и пишет дату отписки (`subscribed = false`, `unsubscribed_at`; в панели — «отписка <дата>»); строка подписчика с главной удаляется при ближайшем проходе удаления по срокам. Повторное открытие ссылки снова показывает «Вы отписались». Тексты: `content.unsubscribe.lead`, `unsub.wait`, `unsub.done`, `unsub.button`, `unsub.failed`, `unsub.bad`. Код отписки — подпись адреса ключом из свойств скрипта (`unsubKey`, создаётся сам; не удаляйте его — старые ссылки перестанут работать); у одного адреса код всегда один, поэтому отписка снимает все его строки. Новое согласие после отписки подписывает заново.

Как рассылать. Сам скрипт рассылку не отправляет: лимит Gmail (около 100 писем в сутки) общий с письмами о результатах. Для рассылки нужен отдельный сервис (Unisender, Sendsay, Brevo, MailerLite и т. п.): отфильтруйте в таблице строки, где «Рассылка» = `да`, и выгрузите e-mail, имя, язык и ссылку для отписки; ссылку подставляйте в каждое письмо. Перед каждой рассылкой выгружайте список заново, чтобы не написать отписавшимся. Если человек отписался через сам сервис рассылок, в таблице это не отразится — исключайте таких в сервисе. Строкам, записанным до появления галочки, писать нельзя: согласия они не давали.

Тексты: `share.subscribe`, `share.subscribed`, `share.subscribeFailed` (форма), `email.subscribed`, `email.unsubscribe` (письмо), `unsub.*` и `content.unsubscribe` (страница отписки), абзац о рассылке на странице «Конфиденциальность». После правки `share.subscribe` или `email.*` обновите код в Apps Script: текст согласия в таблицу пишет скрипт. Проверка без Google: `node scripts/test-apps-script.js`; в браузере — заглушка `/mock-send` отвечает `subscribed: true` на запрос с согласием. Цели Метрики: `subscribe` (согласие записано) и `unsubscribe`.

### Сравнение двух текстов галочки рассылки (A/B)

С 2026-11-07 (по просьбе заказчика) в формах отправки результата — на экране «Результат готов» и в «Отправить на e-mail» — показывается один из двух текстов галочки согласия на рассылку: А — `ui["share.subscribe"]` («Хочу получать советы по своему профилю DISC…»), Б — `ui["share.subscribeB"]` («Присылайте мне советы… — не чаще раза в неделю»), на всех 13 языках (нерусские носители не видели). Оба текста не выходят за цели рассылки в политике (п. 2.2 русской): материалы о DISC, новые тесты, советы по карьере, новости, рекламные предложения; слово «рекламные» есть в обоих.

- **Доля Б** — `"subscribeAB"` в `site.config.json` (0.5; 0 или нет ключа — только А). Жребий — при каждом открытии страницы, не хранится (`SUB_V`, `subLabel()` в `src/template.html`).
- **Какой текст в базе.** Сайт присылает вариант (`subV: 'a'|'b'`) вместе с согласием; сервер пишет в `results.consent_text` текст именно этого варианта (`consent` или `consentB` ядра, `subscribe()` в `private/server/src/main.js`). Поэтому подписчиков по вариантам можно считать и на сервере — по началу `consent_text`.
- **Цели аналитики:** `nl-a` / `nl-b` — e-mail с результатом отправлен, галочка была видна (человек ещё не подписан); `nl-a-yes` / `nl-b-yes` — сервер подтвердил подписку. Доля подписавшихся = `nl-x-yes` / `nl-x` по визитам.
- **Итог.** Оставить победителя: его текст — в `share.subscribe`, `subscribeAB` убрать (или 0). Сначала сервер (ядро), потом сайт.
- **Закончено 2026-11-11** (решение заказчика: не обещать частоту писем) — `"subscribeAB": 0`, все видят текст А. Итоги — по данным 7–11 ноября. `share.subscribeB` **из локалей не удалять**: ядро берёт из него `consentB`, по которому очередь распродажи (`weeklyTexts` в `private/server/src/sale.js`) узнаёт подписавшихся с обещанием «не чаще раза в неделю» (185 адресов на 11.11) и соблюдает его для них и дальше. Если когда-нибудь менять тексты Б — прежние тексты нужно сохранить в списке `weeklyTexts`, иначе сервер перестанет их узнавать.

### Письмо подписчикам о расширенном отчёте

С 2026-10-25 (решение заказчика; сценарий и тексты — `private/MAILING-PLAN.md`, раздел 0). Одно письмо с призывом купить расширенный отчёт тем, кто согласился на рассылку в форме отправки результата. **Включается строкой `MAILING=on` в `/etc/disc/api.conf` — включает заказчик**; без неё сервер писем не шлёт (в журнале службы при запуске: «письмо подписчикам о расширенном отчёте: выключено»).

- **Кому.** Адрес с согласием на рассылку из формы результата (`results.source = 'result'`, подписка без отписки) в языке, где отчёт продаётся и есть тексты письма (`content.mailing.promo`; с 25.10.2026 во всех языках с покупкой: ru — днём, en, pt, es, fr, de, id, pl, tr, zh, zh-hant — вечером, ja — с 31.10.2026; нерусские тексты носитель ещё не видел); письмо с результатом на этот адрес ушло; на адрес нет оплаченного или возвращённого заказа, нет заказа за последние сутки и нет отчёта по коду доступа. Подписчики с главной письмо не получают (нет профиля).
- **Когда.** Через 3 часа после согласия, в любой час суток (с 2026-11-01, решение заказчика; до того — через сутки, в тот же час суток; `DELAY_HOURS` в `private/server/src/promo.js`). Одно письмо на адрес навсегда (таблица `promo_mails`: вместо адреса — его отпечаток sha256). Пределы: не больше 60 таких писем за сутки и только пока всех писем за сутки меньше 120. При сбое почты — повтор не раньше чем через 20 часов, не больше трёх попыток.
- **Что в письме.** Тема с именем и профилем, скрытый анонс с самой низкой шкалой, логотип (четыре точки разметкой), четыре шкалы, строка о самой низкой шкале, тезисы, листы образца, карточка покупки по обычной цене, ссылка отписки. Ссылки — на страницу отчёта с результатом человека и меткой `?src=nl` (точка продажи `nl` в заказах). Строки — `content.mailing.promo`; тезисы, подпись к листам, кнопка и «бесплатно» — из `product.block`, гарантия — `product.pay.guarantee`. Сборка — `composePromoMail` в `src/apps-script.template.js`.

Адрес картинки одинаков для всех: следить по нему за открытиями нельзя.
- **Цена в письме (с 2026-11-01).** Специальная со сроком — если она включена в панели, задана в валюте языка и до конца её срока (от времени теста в коде результата, срок — из панели) осталось не меньше часа (`offerFor`, `OFFER_LEFT_MIN` в `promo.js`): зачёркнутая обычная, крупно специальная и строка `content.mailing.promo.offerNote` (`{duration}`, `{price}`, `{offerPrice}`; в русской — ещё `{untilMsk}`: «1 ноября 23:43» по Москве — в нерусских Россия не называется; имя с заглавной буквой валидатор между языками не сверяет), в текстовой части — `offerVs`. Иначе — обычная цена, как раньше. Своей цены у письма нет: сервер оплаты принимает специальную цену по тому же времени теста. Страница отчёта, открытая по ссылке письма (`?src=nl`), считает срок от времени теста в письме, а не от первого прохождения на устройстве (`src/pay.js`).

### Экран «Результат готов» с e-mail после теста

С 2026-11-01 (по просьбе заказчика, чтобы расширить базу адресов; проверка на половине посетителей). После ответа на последний вопрос части прошедших тест показывается экран «Результат готов»: «Куда прислать краткий отчёт в PDF и ссылку на результат?», поле e-mail, две галочки (согласие на обработку данных и на рассылку), кнопка «Прислать и показать результат» и ссылка «Показать результат без e-mail».

- **Кому.** Доля `emailStep` в `site.config.json` (сейчас `1` — всем, с 2026-11-08, решение заказчика по итогам A/B-теста; 1–8 ноября было `0.5`): жребий при каждом прохождении, нигде не хранится. Только после ответов на сайте (`finishResult(…, 'finish')`, не с бумажного бланка), когда результат можно отправить (`resultEmail`, `sendEndpoint`) и в браузере ещё нет e-mail (`disc.who`).
- **Вид.** Как у теста: в шапке «Тест пройден», полоса прогресса заполнена, «Пройдено 100 %», меню разделов и подвала нет; форма во всю ширину колонки (решения заказчика по макету `private/mockups/email-step-ru.html`).
- **Отправка.** Та же, что у формы «Отправить на e-mail» в карточке «Сохраните результат» (`renderReport(r, {own:true, send:true})`): то же письмо и та же строка в базе — тексты о данных не менялись. Имени нет (решение заказчика): `disc.who` пишется с пустым именем.
- **Без имени.** Письма начинаются с `ui["email.greetingNoName"]` (`greet()` в ядре; значения — как `content.mailing.promo.greetingNoName`). В форме покупки (экран результата, карточка вернувшегося посетителя, страница отчёта) у результата без имени над e-mail стоит поле «Имя для отчёта» (`content.product.pay.nameLabel`, `nameHint`, `nameRequired`; `withName` в `payForms`, `src/pay.js`): без него заказ и код доступа не отправляются, имя попадает в код результата заказа и запоминается в `disc.last` и `disc.who`.
- **Цели** (заводит заказчик в кабинете системы веб-аналитики): `estep-show` — экран показан, `estep-none` (при `emailStep: 1` не приходит) — подходил, но не показан, `estep-send` — прислал e-mail, `estep-skip` — пропустил. Сравнение: визиты с `estep-show` против визитов с `estep-none` — доля `ext-pay-done` и `email`.
- **Выключить или изменить долю** — `emailStep` в `site.config.json`, сборка, публикация.

### Подарочные сертификаты на расширенный отчёт

Ключ — `"giftBuy": true` в `site.config.json` (условие — `hasGift()` в `build.js`); тексты — `content.gift` в локали (валидатор требует его вместе с `product.pay`, как и `ui["nav.gift"]` и `policy.purchaseGift`) (страница, сертификат `cert`, письма `mail` и `rmail`, карточка на «Услугах» `services`), пункт подвала — `ui["nav.gift"]`.

### Подписка на рассылку с главной страницы

С 2026-10-22 (по просьбе заказчика) на стартовом экране всех 13 языков стоит форма подписки (с 2026-10-25 — после коротких вопросов о тесте, перед списком 16 профилей, вместе с анонсом сервиса резюме; раньше — между ссылками «Четыре стиля · 16 профилей» и «Что вы получите»): поле e-mail, «Подписаться», галочка согласия на обработку данных (`pd.consent`) и отдельная галочка согласия на рассылку (`ui["nl.consent"]`: новые тесты, советы по карьерному росту и трудоустройству, новости сайта и рекламные предложения). - **Где хранится**: в той же таблице, что и согласившиеся на рассылку в форме результата, — строка `results` без результата (`source = 'home'`: кода, профиля и баллов нет). Отметка о согласии на обработку — `consents.kind = 'subscribe'`.
- **Подтверждение (double opt-in)**: на адрес уходит письмо (`content.subscribeMail`, ядро — `composeSubscribeMail()`) со ссылкой `/<язык>/subscribe/#c=<ключ>`; рассылка начинается только после подтверждения: страница сама отправляет ключ серверу при открытии (`{action: 'confirmSubscribe', c}`) и пишет «Подписка подтверждена» — нажимать ничего не нужно (с 2026-10-22, по просьбе заказчика); запрос шлёт скрипт страницы, поэтому сканеры ссылок, которые только скачивают страницу, подписку не подтверждают. Кнопка «Подтвердить подписку» появляется только для повтора после сбоя (`content.subscribeConfirm`, `ui.subc.*`, строка `subc.wait` на время запроса). Ключ `#c=…` — хэш с личными данными: `dataHash()` убирает его из адреса до загрузки счётчика, как `#r=` и `#u=`. Ответ сайту одинаков, подписан адрес или нет; писем подтверждения — не больше 3 в час на адрес.
- **Сроки**: неподтверждённая строка удаляется через 7 дней, отписавшаяся — при ближайшем проходе удаления по срокам (`retention.js`). Отписка — та же страница `/unsubscribe/#u=…` и тот же код отписки, что у подписчиков из формы результата.
- **Тексты о данных** (13 языков): `ui.privacy`, `ui["pd.cookieDetails"]`, абзацы о рассылке и сроках в `content.policy`, третья цель и срок в `content.consentDoc`, п. 2.2 русской политики. Форма, ключ и эти тексты меняются вместе. Нерусские тексты формы и данных носители ещё не видели.
- **Рассылки нет**: подписчики копятся в базе; письма серии (`private/MAILING-PLAN.md`) не отправляются, пока заказчик не утвердит тексты. У подписчиков с главной нет профиля — серия, построенная на ведущем стиле, им не подходит.
- **Проверка на сервере**: `sudo -u disc bash -c "cd /srv/disc/app && node test/subscribe-check.js"` (вторая копия службы без писем, 20 проверок, свои строки убирает).

### Расширенный отчёт: письмо покупателю

**Просьба об отзыве** (с 2026-10-26, по просьбе заказчика; все языки с покупкой): в письме с отчётом после строки «если что-то не так — ответьте на это письмо» стоит серая карточка «Расскажите, пригодился ли отчёт» — ответить парой строк, когда отчёт прочитан (что точно, что нет, что уже попробовали); мелкой строкой — что отзыв покажем на сайте только с разрешения, написанного в ответе, **без имени и других данных** (`extendedMail.reviewTitle`, `review`, `reviewConsent`; `composeExtendedMail` в ядре). Отзыв с именем на сайте — распространение персональных данных: нужно отдельное согласие по ст. 10.1 152-ФЗ, ответа на письмо для этого мало (решение заказчика от 2026-10-26: публиковать без имени). Ответы приходят на `info@`. После правки текстов — сборка, `test-apps-script.js`, выкладка сервера.

Расширенный отчёт (платная услуга) собирает не этот скрипт, а сервер сборки: закрытый репозиторий `Man-You-Can/disc-extended-report`, сценарий GitHub Actions «Собрать отчёт». Если при запуске сценария указан e-mail покупателя, сервер передаёт готовый PDF этому скрипту запросом `{action: 'extended'}`, а скрипт:

- отправляет покупателю письмо с PDF во вложении с адреса `SENDER_EMAIL` (тексты — раздел `content.extendedMail` локали; он есть только в языках, где отчёт продаётся, — `ru.json` и с 2026-10-19 `en.json`; в письме для другого языка скрипт откажет);
- записывает результат в таблицу, если его там ещё нет, и ставит отметку в столбце **Расширенный отчёт**: «отправлен <дата и время> на <адрес>, заказ <номер>» (столбец добавляется справа при первой отправке; повторная отправка дописывается через «; »);
- если сборка оставила замечания (сбалансированный профиль, полупустой лист), отчёт всё равно уходит покупателю, а на адрес формы обратной связи приходит письмо с замечаниями.

Запрос проверяется не токеном сайта (он виден в коде страниц), а отдельным секретом. Его нужно задать в двух местах одним и тем же значением:

1. в закрытом репозитории — секрет `DELIVERY_SECRET` (Settings → Secrets and variables → Actions);
2. в проекте Apps Script — **Настройки проекта** (шестерёнка слева) → **Свойства скрипта** → свойство `extendedSecret`.

В код секрет не попадает: `Code.gs` лежит в открытом репозитории. Пока свойство не задано, скрипт такие запросы отклоняет (`forbidden`). Проверка: `curl -sL -A "Mozilla/5.0" <sendEndpoint>` отвечает `"extended":true`, когда развёрнута версия с приёмом отчётов и секрет задан.

Ограничения: до 5 отчётов на один адрес в час; PDF до 15 МБ; суточный счётчик писем с результатами (`MAX_PER_DAY`) расширенные отчёты не расходуют — запас до лимита Gmail (100 писем в сутки) оставлен для них. Если Gmail письмо не принял, сценарий на GitHub завершается ошибкой (GitHub пришлёт уведомление), а в столбце остаётся «ошибка <дата>: <причина>»; PDF при этом лежит в артефакте запуска.

Как собрать и отправить отчёт — `private/extended-report/EXTENDED-REPORT.md`, раздел 14.

## Страницы «Услуги», «Публичная оферта» и «Условия возврата» (платная услуга)

**Срок и гарантия (редакция от 21 октября 2026).** На витрине отчёт приходит «сразу после оплаты» (сервер отправляет его за десятки секунд); в оферте 24 часа остаются предельным сроком (п. 4.2), невыполнение которого даёт право на возврат. ### Оплата расширенного отчёта (страницы сайта)

Покупка включается одной настройкой: `"payEndpoint"` в `site.config.json` — адрес сервера оплаты без косой черты в конце (например, `https://api.disc-test.org/pay`). Пока ключа нет или он пустой, сайт собирается как раньше: заявка вместо покупки, страниц «Спасибо» и «Оплата не прошла» нет. Сам сервер оплаты в этот репозиторий не входит: он написан на своём сервере 2026-10-11, с 2026-10-12 работает в боевом режиме, и ключ вписан в `site.config.json` (`private/server/src/pay.js`, состояние — `private/infra/SERVER.md`, раздел «Оплата расширенного отчёта») и выключен до проверки на демо-терминале банка; его адрес для `payEndpoint` — `https://api.disc-test.org/pay`. Из этого репозитория сервер берёт цену (`servicePriceRub` → `EXTENDED_PRICE_RUB` в ядре), название услуги для платёжной страницы и чека (`content.services.name`) и письмо-напоминание о неоконченной оплате: тексты — `content.product.pay.remind` в локали, вёрстка — `composePayRemindMail` в `src/apps-script.template.js`. После их правки — `node build.js`, `node scripts/test-apps-script.js` и выкладка на сервер.

Что появляется при заданном `payEndpoint` (только в языках с `content.product.pay` в локали, сейчас это русский, английский, португальский, испанский, французский, немецкий, индонезийский, польский, турецкий, китайский (`zh`), традиционный китайский (`zh-hant`), японский (`ja`) и арабский (`ar`): сервер оплаты отправляет русские заказы в Т-Банк, остальные — в Prodamus, в долларах; страница «Спасибо» передаёт в цель `ext-pay-done` валюту языка — `content.services.currency`):

- **Страницы `/ru/extended-report/thanks/` и `/ru/extended-report/failed/`** — на них банк возвращает покупателя после оплаты и после отказа. Закрыты от индексации, в sitemap не входят. Тексты — `content.product.pay.thanks` и `content.product.pay.fail`.

Логика страниц — `src/pay.js`. Что сайт ждёт от сервера оплаты:

| Запрос | Тело или параметры | Ответ |
| --- | --- | --- |
| `POST <payEndpoint>/order` | JSON без заголовка `Content-Type` (простой запрос, без предварительного `OPTIONS`): `code` — код результата `DISC1.…`, `email`, `source` — источник покупки, `lang` | `{"ok": true, "order": "<номер>", "key": "<ключ заказа>", "url": "<платёжная страница, только https>"}` либо `{"ok": false, "error": "bad email"}` (сайт покажет «Проверьте адрес»), любая другая ошибка — «Не удалось перейти к оплате» |
| `GET <payEndpoint>/status?order=…&key=…` | номер и ключ заказа из ответа выше | `{"ok": true, "status": "new" \| "paid" \| "sent" \| "failed" \| "refunded"}` |

Сервер должен разрешать запросы с адреса сайта (`Access-Control-Allow-Origin`) и возвращать покупателя на `…/extended-report/thanks/?order=<номер>` после оплаты и на `…/extended-report/failed/?order=<номер>` после отказа. Номер заказа — латинские буквы, цифры, `-` и `_`, от 4 до 50 знаков.

Заказ, созданный в браузере покупателя, хранится в `localStorage` (ключ `disc.pay`: номер, ключ, e-mail). По нему страница «Спасибо» показывает адрес покупателя и статус («Ждём подтверждения оплаты от банка» → «Оплата получена, отчёт готовится» → «Отчёт отправлен»), опрашивая сервер раз в 4 секунды, не дольше двух минут. Если страницу открыли в другом браузере, она показывает общий текст и номер заказа из адреса.

**Источник покупки** (`source`): `result-block` и `result-bar` — блок об отчёте и закреплённая кнопка экрана результата, `site-bar` — закреплённая кнопка на остальных страницах сайта (с 2026-10-22; переход на страницу отчёта) (`result-top` — верхний призыв, убранный 2026-10-21, остаётся в старых заказах), `home` — карточка вернувшегося посетителя на стартовом экране (с 2026-10-22 — заказ из формы в самой карточке; переход по её ссылкам на страницу отчёта — отметка в `sessionStorage`, ключ `disc.src`), `services` — переход со страницы «Услуги», `page` — всё остальное. Для ссылок из писем, PDF и бота — параметр `?src=<метка>` в адресе страницы отчёта (строчные латинские буквы, цифры и `-`, до 20 знаков).

**Цели Метрики** (завести в кабинете как «JavaScript-событие» до включения оплаты): `ext-page-buy` — нажата «Купить»; `ext-pay-start` — заказ создан, покупатель ушёл на платёжную страницу; `ext-pay-error` — сервер оплаты не ответил или отказал; `ext-pay-done` — открыта страница «Спасибо» (один раз на заказ, с параметрами `order_price` и `currency`); `ext-pay-fail` — открыта страница «Оплата не прошла». Цель `ext-page-order` (заявка) после включения оплаты срабатывать перестанет.

**Специальная цена на час после теста** (с 22 октября 2026, решение заказчика; во всех языках с покупкой). `servicePriceRub`/`servicePriceUsd`/`servicePriceEur` — обычная цена (790 ₽ / 9,99 USD / 9,99 €), `offerPriceRub`/`offerPriceUsd`/`offerPriceEur` — специальная (490 ₽ / 6,99 USD / 6,99 €), `offerMinutes` — срок (60) в `site.config.json`. Оферта п. 3.1 называет специальную цену во всех 13 языках (`{offerPrice}` подставляется и там, где покупки нет). Включается в языке с этой валютой, где есть покупка и тексты `content.product.pay.offer` (`regular` — подпись к зачёркнутой цене для экранных чтецов; `cta`, `note`, `left` — красная плашка над полем e-mail: призыв «Успейте купить за 490 ₽», пояснение о сроке и крупный отсчёт с подписью «Осталось»; `expired`); в текстах специальная цена — `{offerPrice}` (оферта, п. 3.1). Форма покупки показывает плашку с призывом и отсчётом, зачёркнутую обычную цену и специальную, закреплённая кнопка — специальную цену (`promo.button` с ней). Срок — от более раннего из двух моментов: прохождение этого результата и первое прохождение на устройстве (`localStorage` `disc.offer`; о нём сказано в `pd.cookieDetails`). Заказ шлёт показанную цену (`price`); сервер принимает 490 только в течение 60 минут (+2) от времени прохождения в коде результата, иначе отвечает `offer expired`, и форма переключается на обычную цену. Ключ `pay.offer` обязателен при `product.pay` (валидатор); при открытии покупки в новом языке его тексты пишутся вместе с остальными. Выключить: убрать `offerPriceRub` и `{offerPrice}` из оферты (сборка остановится, если подстановка останется без цены), вернуть `servicePriceRub`, собрать, выложить сервер и опубликовать сайт вместе. Заглушка `scripts/serve.js` проверяет срок так же, как сервер.

**Переключатель специальной цены на «Сводке» панели** (с 25 октября 2026, по просьбе заказчика). Карточка «Специальная цена после теста» сразу под «Сегодня и неделю назад» включает и выключает специальную цену во всех языках сразу, без сборки сайта: кнопка пишет `site_settings.offer` (`on` | `off`) в базу сервера и строку в «Журнал». Сервер оплаты (`offerOn` в `private/server/src/pay.js`, не реже раза в 10 секунд) при выключенной отвечает на заказ по специальной цене `offer off` с обычной ценой. Сайт спрашивает `GET <payEndpoint>/offer` → `{ok, offer}` (`discOffer` в `src/common.js`; адрес для закреплённой кнопки — `offerUrl` в `window.DISC_XBAR`) только у посетителя, у которого идёт его час после теста; до ответа и при сбое — обычная цена; в запросе нет данных о посетителе — ничего в него не добавлять, иначе править тексты о данных. Ответ `offer off` (выключили при открытой странице) переводит формы и закреплённую кнопку на обычную цену. **Сервер выкладывается раньше сайта**: без адреса `/pay/offer` сайт специальную цену не покажет. Заглушка: `GET /mock-pay/offer?set=off` и `?set=on`. Оферта п. 3.1 (с редакции от 25 октября 2026 г., во всех 13 языках) говорит, что Исполнитель вправе предлагать специальную цену и в любой момент начинать и прекращать это предложение, что она действует, только пока сайт показывает её с оставшимся сроком, и что прекращение не затрагивает оформленные заказы.

**Цены и срок из панели** (с 25 октября 2026, по просьбе заказчика). В той же карточке на «Сводке» под «Цены и срок» — обычная и специальная цена в рублях, долларах и евро и срок специальной цены в минутах (5–1440); проверка: числа положительные, рубли целые, доллары и евро — до двух знаков, специальная меньше обычной. Хранятся в `site_settings` (`price_rub`, `offer_rub`, `price_usd`, `offer_usd`, `price_eur`, `offer_eur`, `offer_min`; нет записи — значение из ядра, то есть `site.config.json`), модуль `private/server/src/prices.js`: сервер оплаты принимает заказ только по текущим ценам (другая — отказ `price` с обычной ценой), письма и PDF берут цену в момент сборки письма (`core.setPrices` → переменные ядра `EXTENDED_*`; в данных ядра у `promo.price` и `reportAd.price` стоит `{price}`, его подставляет `extPriceText`), `GET /pay/offer` (и `/pay/prices`) отдаёт `{ok, offer, minutes, prices: {RUB: {regular, offer}, USD, EUR}, langs: {<язык>: {regular, offer}}}`.
- **Цены по языкам** (с 31 октября 2026, решение заказчика: по разбору конверсии нажатий «Купить»). У каждого языка с оплатой через Prodamus может быть своя пара «обычная / специальная» в валюте языка (доллары или евро) — она заменяет в этом языке общую цену валюты; язык без своей цены берёт общую. Русская версия — только рубли. В панели — строки «Свои цены языков» в той же форме «Цены и срок» (пустые обе — общая цена, серым подсказкой); в базе — `site_settings.lang_prices` (JSON `{язык: [обычная, специальная]}`; пока записи нет — `langPrices` из `site.config.json` через ядро, `EXTENDED_LANG_PRICES`). Сервер оплаты (`prices.cents(P, валюта, язык)`), письма и PDF (`extPriceText(cur, locale, lang)`), `GET /pay/offer` (`langs`), сайт (`window.DISC_PRICE.lang`, `discPriceNow` берёт `langs[язык]` раньше `prices[валюта]`) и сборка (`langPair` в `build.js`; `livePrices` обновляет и `langPrices`) — все знают о цене языка. Порядок выкладки: сначала сервер, потом сайт — старый сервер не отдаёт `langs`, и страница при открытии подменила бы цену языка общей. Первые цены (31.10.2026, по слову заказчика): es и pl — 7,99 / 4,99 USD; pt, tr, zh — 4,99 / 2,99; id — 3,99 / 2,49; остальные — общие 9,99 / 6,99 USD и EUR. Комиссия Prodamus по зарубежным картам — 10 % (на его странице тарифов — «10 %, но не менее 100 ₽»; на настоящей оплате 1 $ 19.10.2026 удержано ровно 10 %).
- **Сайт.** Сборка ставит в тексты значения на момент сборки, обёрнутые невидимыми метками: U+2063 — обычная цена, U+2062 — специальная, U+2061 — срок словами (`{duration}`: «1 час», «30 минут», через `Intl`), U+2064 — скидка пакета кодов на «Для организаций» (в разметке — `<span data-dpct>`). `src/common.js` (`discPriceApply`, наблюдатель за изменениями страницы) подменяет текст между метками на текущие значения из ответа сервера, формы покупки и закреплённая кнопка берут оттуда же числа для заказа и отсчёта. Запрос уходит, только когда цена на странице видна (скрытая закреплённая кнопка не в счёт) или у посетителя идёт его срок после теста; в нём нет данных о посетителе. В `<title>`, `<meta>` и JSON-LD меток нет — там цена со сборки (`finishMarks` в `build.js`); поэтому `node build.js` перед сборкой спрашивает текущие цены у сервера и обновляет `site.config.json` (`NO_LIVE_PRICES=1` — не спрашивать). Метки нельзя вписывать в тексты вручную, а U+2060 — соединитель слов в текстах лендинга резюме, меткой он не служит.
- **Тексты.** В плашке специальной цены вместо «час» — `{duration}` (`content.product.pay.offer.note`, `expired` без упоминания часа); п. 3.1 оферты на 13 языках цен и срока не называет.
- **Заглушка.** `GET /mock-pay/offer?rub=990&offerRub=590&usd=…&offerUsd=…&eur=…&offerEur=…&min=30` меняет цены и срок заглушки; заказ с другой ценой — отказ `price`.
- **Не берут цены из панели:** бот в Telegram (свой `Code.gs` в Apps Script) и описания страниц для поисковиков до следующей публикации.

**Оплата в евро** (с 22 октября 2026, решение заказчика): во французской и немецкой версиях `content.services.currency` — `EUR`, цены — `servicePriceEur` (9,99) и `offerPriceEur` (6,99), в текстах «9,99 €» с неразрывным пробелом, в оферте п. 3.1 — «euros» / «Euro», в шагах покупки — «Vous payez en euros» / «Sie bezahlen in Euro». Валюта уходит в ядро (`DATA[язык].pay.currency`), и сервер оплаты (`private/server/src/pay.js`, `intlCurrency`) создаёт заказ Prodamus в евро; доход Prodamus в панели и в письме за месяц считается по валютам отдельно (доллары и евро не складываются). Перевести ещё один язык на евро: `currency: "EUR"` в `content.services` его локали, «USD»/«доллары» в его текстах — на «€»/«евро», сборка, `test-apps-script.js` (проверка валюты по языкам — в нём), выкладка сервера, публикация. В `scripts/serve.js` заглушка выбирает евро для fr и de — добавить язык и туда.

### Для организаций: страница и коды доступа

С 22 октября 2026, по просьбе заказчика, в русской версии; с 12 ноября 2026 — во всех 13 языках (нерусские тексты носители не видели; `private/B2B-PLAN.md`). Организация, консультант или тренер покупает расширенные отчёты пакетом и раздаёт людям коды доступа; человек проходит тест и вводит код вместо оплаты. - **Другой язык**: появится вместе с `content.cv` и `content.cvPromo` в его локали. Бесплатный тариф в строке тарифов «Услуг» показывается словом из `per` (проверка цены — «0 ₽», «$0», «0 美元», «0 €»); цена «от …» — `services.price` с `{price}` (в английском «{price} to start», в китайском «{price}起», в немецком «{price} zum Start»). В китайском внутри «专属价格。» в `note` и `services.text` стоят соединители U+2060 (иначе на телефоне «格。» переносилось отдельно).

## Страница «Как готовятся отчёты»

`/how-reports-are-made/` в каждом из 13 языков (с 2026-10-14; русский текст — исходный и утверждён заказчиком): как готовятся краткий и расширенный отчёты — тексты написал искусственный интеллект по правилам редакции, расчёт и сборку делает программа, правила и проверка остаются за человеком; что это даёт участнику, чего отчёт не делает, вопросы и ответы (с разметкой FAQPage). Пункт «Как готовятся отчёты» стоит в шапке перед «Услугами».

- **Тексты** — `content.howMade` и `ui["nav.howMade"]` в локали. Оба ключа обязательны в каждой локали (валидатор): страница и пункт в шапке есть во всех языках, у страницы `hreflang` на все 14 версий. Подстановки: `{results}`, `{contact}`, `{privacy}` — ссылки на «Расшифровку результатов», «Обратную связь» и «Конфиденциальность», `{price}` — цена расширенного отчёта. В `steps` и `limits` допустим `<b>`.
- **Страница описывает то, что есть на самом деле.** Тексты отчётов написаны заранее, в момент заказа ИИ не участвует; расчёт идёт по формуле; расширенный отчёт собирает сборщик по коду результата (`private/extended-report/EXTENDED-REPORT.md`, раздел 4) и сервер отправляет его без проверки человеком; сторонним ИИ-сервисам ответы, имя и e-mail не передаются; русские шаблоны всех 16 профилей заказчик прочёл до продажи. Если что-то из этого меняется (правила выбора блоков, порядок отправки, срок, цена, появление ИИ в сборке), текст страницы правится вместе с изменением.
- **Модель ИИ и её разработчик на странице не называются** (решение заказчика от 2026-10-14): «искусственный интеллект», «большая языковая модель».
- **12 нерусских версий.** Смысл тот же, что в русском тексте (те же разделы, восемь плюсов, четыре ограничения, пять вопросов), но текст написан заново под читателя языка, а не переведён. Фактические отличия: расширенный отчёт на этих языках не продаётся — о покупке, оплате и доставке сказано так же, как в `content.product` и `content.services` локали (заявка; после заказа — письмом не позднее 24 часов после оплаты), без срока появления отчёта и без слов «обычно в течение нескольких минут»; о подготовке расширенного отчёта говорится как о порядке, действующем для отчёта на любом языке (в настоящем времени, а не как о состоявшейся продаже); цена — `{price}` в записи локали; страна хранения данных не называется. Утверждения о проверке человеком не смягчаются (вводные заказчика от 2026-10-14: краткие отчёты на этих языках смотрели живые люди, расширенные будут вычитаны целиком до запуска продаж).
- **Правка текста.** Страница описывает действующий порядок подготовки отчётов: если он меняется, текст правится во всех 13 языках сразу. Когда в языке появляется покупка (`content.product.pay`), слова о заявке на странице этого языка заменяются словами о покупке — как в русской версии.

## Бот в Telegram

Справочный бот для русской версии: нужен как ресурс для проверки платёжной системой (в описании бота стоят имя и ИНН исполнителя) и как ещё один вход на сайт. На `/start` показывает три кнопки: «Пройти тест бесплатно» (ссылка на `/ru/`), «Расширенная версия — 490 ₽» (описание услуги, срок, ссылки на страницу услуги, оферту и условия возврата, реквизиты) и «Задать вопрос» (форма обратной связи и `feedbackEmail`). Команды `/service` и `/help` открывают те же экраны. Оплату бот не принимает, сообщения пользователей не хранит и никуда не пересылает; в группах молчит.

Скрипт `backend/telegram-bot/Code.gs` генерируется сборкой из `src/telegram-bot.template.js`: цена — `servicePriceRub`, реквизиты — `ui.legal` русской локали и `legalInn`, название услуги — `content.services.name`, адрес для вопросов — `feedbackEmail`. Остальные тексты бота лежат в шаблоне (бот одноязычный, в локали они не вынесены). Файл собирается, только если есть всё, на что бот ссылается: русская версия с офертой, цена в рублях, ИНН и страница обратной связи. Проверить без Google и Telegram: `node scripts/test-telegram-bot.js`.

### Как развернуть (один раз, около 10 минут)

1. В Telegram откройте [@BotFather](https://t.me/BotFather) → `/newbot`. Имя — например `DISC Test`, адрес — любой свободный, оканчивающийся на `bot` (например `disc_test_org_bot`). BotFather пришлёт **токен** вида `1234567890:AA…` — это пароль от бота, не публикуйте его и не вставляйте в код. Картинка профиля — `backend/telegram-bot/avatar.png`: команда `/setuserpic`, выбрать бота, отправить файл как фото (рисуется в `scripts/make-assets.js`).
2. Откройте https://script.google.com → **Новый проект** (отдельный от проекта с письмами). Замените содержимое `Code.gs` содержимым `backend/telegram-bot/Code.gs`, сохраните (⌘S).
3. **Настройки проекта** (шестерёнка слева) → **Свойства скрипта** → добавьте свойство `BOT_TOKEN` со значением-токеном.
4. **Развернуть → Новое развёртывание → тип «Веб-приложение»**: «Выполнять от имени» — *Я*; «У кого есть доступ» — *Все*. Нажмите **Развернуть**, разрешите скрипту обращаться к внешним сервисам, скопируйте **URL веб-приложения** (`https://script.google.com/macros/s/…/exec`).
5. В **Свойствах скрипта** добавьте `WEBAPP_URL` с этим адресом.
6. В редакторе выберите функцию `setup` и нажмите **Выполнить**. В журнале появится «Бот @… настроен: вебхук, команды, описание». Функция сама ставит вебхук, меню команд, «Описание» и «О боте» с реквизитами — в BotFather их вписывать не нужно.
7. Откройте бота в Telegram, нажмите **Запустить** и пройдите по кнопкам.

Если бот молчит: выполните функцию `status` — в журнале будет последняя ошибка вебхука. Чаще всего доступ к веб-приложению выставлен не «Все» или `WEBAPP_URL` указывает на адрес `/dev` вместо `/exec`.

После смены цены, реквизитов или текстов: `node build.js`, замените код в редакторе, **Развернуть → Управление развёртываниями → ✎ → Новая версия → Развернуть** (URL не меняется) и снова выполните `setup` — она обновит описание бота.

Как это защищено: токен хранится только в свойствах скрипта; в адрес вебхука `setup` добавляет случайный ключ (`WEBHOOK_KEY`), запросы без него игнорируются; повторная доставка одного и того же события пропускается. Скрипт отвечает Telegram через `HtmlService`: ответ `ContentService` отдаётся с переадресацией 302, которую Telegram считает ошибкой.

## Форма обратной связи

Страница `/contact/` (и `/xx/contact/`) — форма «Обратная связь»: имя, e-mail для ответа, тема (обязательная, до 120 знаков; с 2026-10-12), сообщение и файлы. Тема стоит в теме письма владельцу: «Сообщение с сайта disc-test.org: <тема> — <имя>» (с 2026-11-06, по просьбе заказчика: письмо не с русской версии — «disc-test.org: <тема> — <имя>» и сведения под текстом по-английски, чтобы ответ иностранцу не цитировал русских слов; имя, уже стоящее в теме из формы, не повторяется — `contactSubject`, `contactMeta` в ядре); в заявке на расширенный отчёт она подставляется сама, а тема письма остаётся «Заявка на расширенный отчёт — …». Ссылка на неё в шапке (последний пункт верхнего меню) и в подвале каждой страницы, на странице «О проекте» и в «Конфиденциальности». Адрес получателя — `feedbackEmail` в `site.config.json` (сейчас `info@disc-test.org`); пустое значение убирает страницу и ссылки на неё. Почтовый ящик по этому адресу должен существовать (например, пересылка на Reg.ru или Google Workspace) — сайт его не создаёт.

Письма отправляет тот же скрипт Google Apps Script, что и письма с результатом (запрос `{action: "contact"}` в `doPost`): текст сообщения и вложения уходят на `CONTACT_TO`, адрес отправителя подставляется в `replyTo`, так что ответить можно обычной кнопкой «Ответить». В базу результатов сообщения не записываются. Пока `sendEndpoint` пустой, форма работает в запасном режиме: кнопка «Отправить» открывает почтовый клиент посетителя с заполненным письмом на `feedbackEmail`, а под формой показывается пояснение, что приложенные файлы нужно добавить в письмо вручную. После развёртывания Apps Script (см. выше) достаточно вписать `sendEndpoint` и пересобрать — форма начнёт отправлять сообщения сама. Если скрипт уже был развёрнут раньше, обновите его код: **Развернуть → Управление развёртываниями → ✎ → Новая версия**.

Файлы: несколько штук общим размером до 10 МБ (`MAX_CONTACT_BYTES` в скрипте и `maxBytes` в `build.js` — одно число проверяется и в браузере, и на сервере), не больше 20 штук. Файлы читаются в браузере и передаются в JSON в base64, поэтому запрос получается примерно на треть больше суммарного размера файлов; лимит письма Gmail — 25 МБ. Длинные имена в списке файлов показываются как «начало…конец»: имя разбито на две части, первая сжимается с многоточием, хвост с расширением виден всегда (CSS в `src/template.html`, разбиение в `src/contact.js`). Файл, из-за которого общий размер превысит лимит, не добавляется, об этом сообщает всплывающая подсказка.

Защита от спама: токен `sendToken`, скрытое поле-ловушка (заполнившие его боты получают «отправлено», но письмо не уходит), не больше 3 сообщений с одного e-mail в час, общий суточный лимит писем `MAX_PER_DAY` (тот же, что у писем с результатом). Текст письма формируется только на сервере, HTML экранируется.

Тексты формы — ключи `contact.*` и `content.contact` в `src/locales/*.json`, разметка и логика страницы — `src/contact.js`. Проверить без Google: `node scripts/test-apps-script.js` (в том числе вложения, лимиты, ловушка) и локально в браузере — временно впишите `"sendEndpoint": "http://localhost:8765/mock-send"`, выполните `node build.js`, `node scripts/serve.js` и откройте http://localhost:8765/ru/contact/ (заглушка печатает тему, имена и размеры файлов в консоль сервера; `/mock-fail` имитирует ошибку). Не забудьте вернуть пустой `sendEndpoint` перед коммитом. Цель Метрики `contact` срабатывает при успешной отправке.

## Результаты участников

Участник на экране результата получает ссылку вида `…/ru/#r=DISC1.…`; с 2026-10-22 та же ссылка стоит в адресной строке, и в ней нет e-mail (имя входит в код, если оно было указано; с 2026-10-21 сайт имени и e-mail не спрашивает). С 2026-10-22 под отчётом — и в блоке «Сохраните результат» своего результата, и у результата, открытого по ссылке (карточка «Код результата» убрана), — две кнопки: «Поделиться профилем» (`share.profile`) и «Сохранить профиль» (`share.saveProfile`, тот же PDF краткого отчёта, что прежняя «Сохранить в PDF»). «Поделиться профилем» открывает окно (`<dialog>`, `shareButtons()`/`shareDialog()` в `src/template.html`): «Скопировать ссылку» и LinkedIn, Facebook, WhatsApp, Telegram — во всех языках одинаково, в порядке заказчика; в WhatsApp и Telegram уходит строка `share.msg` («Профиль DISC: {name} ({key})») со ссылкой. Ссылка — та же, что в адресной строке (без e-mail); адреса соцсетей собираются в момент нажатия, в разметку страницы ссылка с кодом не пишется. Цели Метрики: открытие окна — `share`, сеть — `share-<сеть>` (`share-linkedin`, `share-facebook`, `share-whatsapp`, `share-telegram`; в кабинете Метрики есть только `share`, остальные нужно завести). «Панель администратора» принимает ссылки так же, как коды. Блок «Поделитесь своим типом» (кнопки соцсетей и «Поделиться типом» со ссылкой на страницу профиля) убран 2026-10-21 по решению заказчика; страница профиля по прежним ссылкам с `?ref=` по-прежнему показывает приглашение пройти тест. Ссылка открывает отчёт на любом языке. Чтобы получать копию каждого результата автоматически, задайте `OWNER_COPY` в скрипте Apps Script.

После развёртывания Apps Script все результаты автоматически собираются в Google Таблицу (см. выше). Панель администратора (`…/ru/#admin` или ссылка в подвале) остаётся для ручной работы: она собирает вставленные коды/ссылки в таблицу и экспортирует её для Excel; эта таблица хранится в браузере администратора.
